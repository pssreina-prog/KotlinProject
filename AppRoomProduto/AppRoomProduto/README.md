1. O que é persistência de dados? O que aconteceria com os produtos cadastrados se, em vez do Room, eles fossem guardados apenas em uma MutableList dentro da MainActivity?
   A persistência de dados refere-se à capacidade de armazenar informações de forma duradoura para que elas sobrevivam ao fechamento do aplicativo, reinicializações do dispositivo ou quedas de energia. No nosso projeto, utilizamos o Room para gravar os produtos na memória não volátil (banco de dados SQLite do celular). Se guardássemos os dados apenas em uma MutableList dentro da MainActivity, essa lista estaria alocada exclusivamente na memória RAM do aparelho. Isso significa que, no momento em que o usuário fechasse o aplicativo, girasse a tela (causando a recriação da Activity) ou o sistema operacional encerrasse o processo por falta de memória, todos os produtos cadastrados seriam perdidos instantaneamente. A lista em memória é puramente volátil e serve apenas para manipulação temporária, enquanto a persistência garante a integridade e retenção do negócio a longo prazo.

2. Qual é a diferença entre usar o SQLite diretamente (com SQLiteOpenHelper e comandos SQL manuais) e usar o Room? Cite pelo menos duas vantagens do Room.
   Usar o SQLite puro através do SQLiteOpenHelper exige que o desenvolvedor escreva manualmente comandos SQL extensos para criar tabelas, gerencie cursores (Cursor) complexos para extrair dados linha por linha e converta esses dados manualmente para objetos Kotlin, o que resulta em muito código repetitivo (boilerplate) e em alto risco de erros de digitação em tempo de execução. O Room atua como uma camada de abstração robusta sobre o SQLite, simplificando drasticamente essa comunicação. A primeira grande vantagem do Room é a verificação de consultas em tempo de compilação; se você errar o nome de uma coluna ou tabela em uma anotação @Query, o Android Studio avisa o erro antes mesmo de você rodar o app. A segunda vantagem é o mapeamento automático de objetos (Object Relational Mapping), onde o Room converte automaticamente as linhas da tabela em instâncias da nossa classe de dados Product, além de possuir suporte nativo e facilitado a corrotinas do Kotlin através de funções suspend.

3. Explique o papel de cada uma das três peças do Room: Entity, DAO e Database. Como elas se relacionam no seu projeto?
   No ecossistema do Room, cada componente possui uma responsabilidade bem definida dentro da arquitetura de dados. A Entity (representada no nosso projeto pela classe Product.kt) define o modelo da tabela e suas colunas, atuando como a estrutura física que será armazenada no banco. O DAO - Data Access Object (representado pela interface ProductDao.kt) contém os métodos que definem as operações que podem ser realizadas no banco, como inserir (@Insert), buscar (@Query) ou atualizar (@Update), encapsulando as instruções SQL. Por fim, o Database (representado por AppDatabase.kt) é uma classe abstrata que une as peças, configura a versão do banco e serve como ponto de acesso central para instanciar o DAO. No nosso projeto, a relação ocorre da seguinte forma: a MainActivity obtém uma instância de AppDatabase, que por sua vez fornece o ProductDao, permitindo que a aplicação execute operações na tabela mapeada pela Entity Product.

4. Por que o Android não permite acessar o banco de dados na thread principal (UI thread)? O que é um ANR (Application Not Responding)? Como suspend e lifecycleScope.launch resolvem esse problema?
   O Android proíbe o acesso direto ao banco de dados na thread principal (responsável por desenhar a interface do usuário) porque operações de I/O (entrada e saída em disco) são imprevisíveis e demoradas. Se a thread principal ficar ocupada esperando o banco responder, ela deixa de atualizar a tela e de responder aos toques do usuário, congelando a aplicação. Caso esse bloqueio ultrapasse cerca de 5 segundos, o sistema operacional exibe a fatídica caixa de diálogo de ANR (Application Not Responding), perguntando se o usuário deseja fechar o app por mau funcionamento. Para resolver isso, utilizamos corrotinas: a palavra-chave suspend indica que uma função DAO realiza uma operação demorada que pode ser pausada e retomada sem bloquear a thread atual, enquanto o bloco lifecycleScope.launch abre uma corrotina assíncrona que executa o código em uma thread secundária de fundo, mantendo a interface totalmente fluida e livre de travamentos.

5. O que faz o fallbackToDestructiveMigration()? Por que ele é perigoso em um app publicado na Play Store? O que seria uma migração (Migration) de banco de dados?
   O método fallbackToDestructiveMigration() instrui o Room a agir de maneira drástica caso a versão do banco de dados seja incrementada (por exemplo, de version = 1 para version = 2 ao adicionarmos o atributo quantity na Entity) e nenhuma regra formal de transição tenha sido programada: ele apaga completamente o banco de dados existente e o recria do zero. Isso é extremamente perigoso em um aplicativo real publicado na Play Store porque, se um usuário atualizar o app, ele perderá todos os dados salvos anteriormente no dispositivo, gerando frustração e avaliações negativas. Uma Migração (Migration), por sua vez, é um script controlado que define como o banco deve evoluir de uma versão para outra (por exemplo, executando um comando SQL ALTER TABLE para adicionar a nova coluna), preservando integralmente os dados que o usuário já possuía antes da atualização.

6. Qual é a vantagem do ViewBinding em relação ao findViewById? Que tipo de erro ele ajuda a evitar?
   O ViewBinding gera uma classe de vínculo para cada arquivo de layout XML inflado, criando referências diretas e tipadas para cada componente visual presente na tela. A principal vantagem em relação ao tradicional findViewById é a eliminação do código repetitivo e a segurança contra tipos (type safety). Com o findViewById, se você tentasse buscar um botão achando que era um TextView, o app crasharia apenas em tempo de execução. Além disso, se houvesse um erro de digitação no ID da view ou se o componente não existisse em uma determinada orientação de tela, o findViewById retornaria null, gerando uma temida exceção de NullPointerException. O ViewBinding garante segurança de nulidade e de tipo em tempo de compilação, tornando a manipulação de componentes na MainActivity muito mais segura e limpa.

7. No tutorial, o banco é criado dentro da MainActivity. Por que em apps maiores é recomendado criar o banco como Singleton (uma única instância para o app inteiro)? O que poderia acontecer se várias telas criassem cada uma o seu banco?
   Criar instâncias do banco de dados Room é uma operação custosa que consome recursos consideráveis de processamento e memória do dispositivo. Em aplicações maiores, se cada Activity ou Fragment criasse a sua própria instância do banco através do Room.databaseBuilder(), teríamos múltiplas conexões abertas simultaneamente apontando para o mesmo arquivo SQLite físico. Isso poderia gerar um alto consumo de bateria, vazamentos de memória, lentidão geral no sistema e graves problemas de concorrência ou corrupção de dados por conflitos de escrita simultânea. O padrão Singleton garante que apenas uma única instância da classe de banco de dados seja criada e compartilhada por todo o ciclo de vida do aplicativo, otimizando o desempenho e garantindo a consistência das transações.

8. Reflexão pessoal: quais foram as principais dificuldades que você teve neste projeto e como as resolveu? Cite um app real (de comércio, saúde, escola etc.) em que a persistência local com Room seria útil e esquema como você o aplicaria.
   Durante o desenvolvimento deste projeto, a principal atenção esteve voltada para a correta configuração assíncrona das operações utilizando corrotinas (lifecycleScope.launch junto com as funções suspend do DAO), garantindo que nenhuma consulta bloqueasse a thread principal. Compreender a necessidade de atualizar a versão do banco no arquivo AppDatabase ao modificar a entidade Product também exigiu cuidado conceitual para entender o comportamento das migrações. Um exemplo real onde a persistência local com Room seria extremamente útil é um aplicativo de controle de estoque para pequenos comércios ou farmácias de bairro. Nesse cenário, o Room permitiria que o balconista cadastrasse produtos, controlasse preços e gerenciasse quantidades mesmo quando estivesse em locais com sinal de internet instável ou totalmente offline. Os dados ficariam seguros localmente no dispositivo e, posteriormente, poderiam ser sincronizados com um servidor em nuvem assim que uma conexão estável estivesse disponível, garantindo a continuidade operacional do negócio sem perda de informações.
